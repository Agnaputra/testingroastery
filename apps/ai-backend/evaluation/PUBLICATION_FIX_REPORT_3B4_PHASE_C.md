## C1.2 Desain otoritas harga efektif test-only

Constraint positif, unik, dan FK/referensi ke daftar SKU hasil migrasi yang disetujui. Harga integer Rupiah, tanpa transformasi ribuan. Catat riwayat revisi atau snapshot sebelum update untuk rollback. **Tidak ada DDL/DML pada DB penelitian/production.**
2. **Baseline satu kali.** Import 31 produk/variant yang benar-benar tersedia dari `apps/web/lib/data.ts` bersama mapping `ACTIVE_CATALOG_MAPPING`; verifikasi 26 pasangannya terhadap field harga KB di `coffee_knowledge.metadata`, dan laporkan lima web-only secara terpisah. Import gagal jika SKU ambigu, nominal kosong/tidak positif, unit tidak cocok, atau slug ganda tak terselesaikan. Snapshot owner/PDF dipakai untuk review bisnis, bukan disalin otomatis ke harga efektif. Setelah baseline, DB test adalah satu-satunya sumber harga runtime; static `data.ts` hanya sumber migrasi dan tidak menjadi fallback saat DB/price authority gagal.
3. **Satu snapshot status + harga.** Service FastAPI `price_service.py`/`catalog_authority_service.py` membaca publication overrides dan harga efektif pada satu transaksi/snapshot konsisten; respons REST memuat `catalog_revision`, `price_revision`, `effective_catalog_fingerprint`, SKU Published dan harga. Public GET tidak mengembalikan harga produk Unpublished. Admin GET terautentikasi dapat membaca harga untuk editor. Semua permukaan web menggunakan helper authority yang sama dengan `cache: no-store`. Jika status/harga tidak lengkap atau service gagal, produk boleh tampil sebagai state unavailable tanpa harga/aksi; cart/checkout harus ditahan. Tidak ada harga static fallback.
4. **Editor admin per SKU.** Ganti empat field generik dengan variant yang benar untuk web product/profile terpilih; untuk master row dengan dua profile, admin memilih profile secara eksplisit. Tampilkan/simpan Rupiah penuh dengan `formatRupiah()` untuk tampilan. Saat cart lama dibuka, bandingkan SKU/revisi harga; tampilkan harga terbaru dan perubahan secara jelas, minta pengguna meninjau ulang sebelum checkout. Tidak pernah mengubah `unitPrice` persisten secara diam-diam sebagai bukti harga transaksi.
6. **Quote dan confirm server.** Tambah REST `POST /api/checkout/quote` dan `POST /api/checkout/confirm` melalui proxy Next.js. Request hanya berisi `sku_id`, quantity, opsi seduh, kode voucher, pilihan pengiriman, dan spesifikasi BYOB; nilai `unitPrice`, subtotal, discount, shipping, total dari client ditolak/diabaikan. Quote mengembalikan nominal, revisi, fingerprint, dan token/ID sementara tanpa PII. Confirm memakai quote tersebut, mengunci/memeriksa revisi dan status lagi, lalu mengeluarkan receipt simulasi dengan nominal server; jika harga/status berubah, balas 409 dan wajib quote ulang + review; outage 503. Simpan receipt test minimal tanpa data pribadi. UI boleh menyimpan order demo lokal hanya setelah confirm berhasil dan memakai nominal server, bukan `getSubtotal()`/`grandTotal` browser. Tidak ada klaim pembayaran nyata.
7. **BYOB dan addon adalah bagian dari gate.** Addon diberi SKU harga efektif. Cart BYOB harus menyimpan slug komponen **beserta rasio dan ukuran**; backend menghitung ulang menggunakan aturan `blend-profile.ts:21-43` yang dikunci dengan conformance tests lintas TypeScript/Python. Jawaban model sebenarnya baru dapat dinilai end-to-end setelah persetujuan API berbayar; mock hanya membuktikan payload dan gate.

**Kontrak kegagalan:** `503 PRICE_AUTHORITY_UNAVAILABLE` untuk DB/outage/incomplete SKU, `409 PRICE_CHANGED` untuk revisi quote/cart tidak cocok, `409 PRODUCT_UNPUBLISHED` bila status berubah, `422 INVALID_SKU_OR_AMOUNT` untuk input admin/checkout. Tidak ada publikasi harga lama sebagai harga yang dapat dibeli. UI menampilkan pesan ringkas dan jalur coba lagi; status publikasi Fase B tetap berlaku.
