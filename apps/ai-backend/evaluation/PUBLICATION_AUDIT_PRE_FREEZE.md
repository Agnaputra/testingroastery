## Sinkronisasi dan risiko

1. **P0 — status tidak seragam pada permukaan publik (VERIFIED dari kode).** Toggle hanya mengubah override DB. List katalog membaca override tetapi fail-open saat error; halaman detail, homepage, search, Coffee Lab, dan whitelist proxy chat menggunakan status statis. Produk yang di-unpublish tetap dapat ditemukan melalui URL detail atau permukaan statis. Perbaikan yang disarankan setelah persetujuan: satu otoritas status runtime untuk semua permukaan publik, dengan perilaku kegagalan yang tidak menampilkan produk yang statusnya belum dapat diverifikasi.
2. **P0 — residu vector dan metadata lama (PARTIAL).** Override false menyaring chunk lama untuk slug yang tepat. Akan tetapi tidak ada pemeriksaan `products.is_active` atau keanggotaan pada daftar KB aktif di SQL, dan hasil vector tidak disaring ulang sebelum konteks/kartu non-recommendation. `app/seed_data.py:44-116` dijalankan manual, mengganti chunk per slug yang di-seed, tetapi tidak menghapus produk/chunk yang keluar dari daftar. Lakukan uji terisolasi terhadap slug orphan/stale tanpa menyentuh database aktif; setelah disetujui, pertimbangkan filter defensif pada seluruh jalur respons dan prosedur rekonsiliasi seed.
3. **P1 — publish/unpublish bukan sinkronisasi konten (VERIFIED dari kode).** Toggle tidak membuat/menghapus embedding atau memperbarui produk. Publish hanya dapat mengaktifkan record yang sudah ada di KB statis/pgvector; produk baru yang hanya ada di owner snapshot tidak menjadi jawaban RAG. `saveProductPrice()` di `apps/web/app/admin/page.tsx:238-263` hanya mengubah React state, tidak tersimpan di DB maupun `data.ts`/KB/embedding. Perubahan atribut/harga dalam kode memerlukan deploy/seed terpisah; selama jeda, jawaban dan harga bisa berbeda. `products` dan `product_variants` bukan sumber harga runtime chat; pada snapshot ini `product_variants` kosong.
4. **P1 — identitas slug ganda (VERIFIED dari kode).** `ACTIVE_CATALOG_MAPPING` memetakan beberapa web slug ke knowledge slug. Toggle CMS mengirim keduanya, tetapi API menerima slug valid apa pun tanpa pemeriksaan pasangan. Override manual yang hanya mengubah salah satu slug dapat membuat frontend/backend berbeda. Uji tiap pasangan mapping dan tetapkan identitas produk kanonik sebelum perubahan arsitektur.
5. **P1 — status dataset saat evaluasi (NOT VERIFIED sampai freeze/runtime).** Saat ini 40 target sesuai snapshot lokal. Jika override atau KB berubah, fingerprint dan status harus diperiksa lagi tepat sebelum freeze dan setiap batch evaluasi. Kandidat yang tidak lagi Published harus diblokir/dicatat sebagai excluded sesuai protokol, bukan diganti diam-diam berdasarkan skor.

## Rancangan integration testing (belum dijalankan)

Gunakan DB dan server test terisolasi dengan salinan data sintetis, admin session/key test, dan OpenAI/retrieval stub yang dapat mengembalikan chunk lama. Jangan menguji toggle pada DB yang saat ini terkonfigurasi. Untuk satu slug biasa dan satu pasangan web/knowledge slug:

1. Baseline Published: admin, `/api/catalog/publication`, `/api/products`, `/api/search`, `/catalog`, detail, homepage/search, `/api/chat`, kartu/action widget konsisten; catat trace context IDs dan fingerprint.
2. PATCH Unpublished: baca kembali override; pastikan SQL pgvector menolak embedding lama; `/api/products`, `/api/search`, rekomendasi dan konteks chat, kartu/action, katalog list dan URL detail semuanya menolak produk. Periksa teks jawaban agar tidak menyebut produk sebagai tersedia.
3. PATCH Published kembali: pastikan produk kembali hanya bila atribut dan embedding sinkron. Untuk produk baru tanpa chunk, sistem harus melaporkan ketidaktersediaan konten alih-alih mengklaim retrieval berhasil.
4. Edit atribut/harga melalui CMS: refresh browser dan server, bandingkan nilai pada frontend, tabel `products`, metadata/chunk pgvector, `/api/products`, dan jawaban. Kegagalan persistensi harus tercatat sebagai temuan, bukan dianggap sukses.
5. Suntik stale chunk, slug orphan, override hanya pada satu dari dua slug mapping, DB outage, dan request chat paralel. Pastikan tidak ada kebocoran status atau konteks lintas request. Semua uji tulis hanya pada DB test yang dapat di-reset.
