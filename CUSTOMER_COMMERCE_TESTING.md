# Customer commerce: local testing

This flow is restricted to an isolated local PostgreSQL database. It does not activate production payments or courier rates.

## Setup

1. Use the existing local `testingroastery` PostgreSQL database. Back it up before running migrations. From `apps/ai-backend`, apply `migrations/20261025_customer_commerce.sql` and then `migrations/20261025_customer_catalog_prices.sql` with `psql -v ON_ERROR_STOP=1 -f <file>` if starting fresh. Apply `migrations/20261026_customer_inventory.sql` afterward, or run `.\.venv\Scripts\python.exe -B -m scripts.apply_customer_inventory_migration` on the local database. The latter refuses remote/production databases and refuses a second application. Existing orders are retained.
2. Install `apps/ai-backend/requirements.txt` in its virtual environment. Copy the blank keys in `apps/ai-backend/.env.example` and `apps/web/.env.local.example` into the corresponding ignored `.env` files. Set `CUSTOMER_COMMERCE_TEST_MODE=1` and `NEXT_PUBLIC_CUSTOMER_COMMERCE_TEST_MODE=1` only for local testing. Both the backend environment and database host must be local. Set `CUSTOMER_TEST_EMAIL_ALLOWLIST` to exact, comma-separated authorized tester email addresses. An empty list denies checkout and payment data. `CUSTOMER_TEST_SHIPPING_IDR` is a flat local test fee, not a courier quote. Zero means no test shipping charge is included; it does not promise free real-world delivery.
3. Keep `PAYMENT_TEST_BCA_ACCOUNT`, `PAYMENT_TEST_BCA_HOLDER`, and `PAYMENT_TEST_QRIS_MERCHANT` in `apps/web/.env.local` only. Put the original JPG at `apps/web/.private/payment/qris-testing.jpg` and set `PAYMENT_TEST_QRIS_PATH=.private/payment/qris-testing.jpg`. `.private/` is ignored by Git. Do not put personal bank details, the QRIS file, or credentials in tracked files.
4. Set finite **synthetic testing inventory** before the first seed: `CUSTOMER_TEST_BEAN_STOCK_GRAMS` per published coffee slug, `CUSTOMER_TEST_ACCESSORY_STOCK_UNITS` per accessory, and `CUSTOMER_TEST_CUP_GRAMS` used per slowbar cup. The values must be supplied by the tester and are not actual owner stock. From the repository root run `node apps/web/scripts/export-customer-catalog.cjs` to inspect the exported coffee, accessory, and BYOB component price snapshot. From `apps/ai-backend`, run `.\.venv\Scripts\python.exe -B -m scripts.seed_customer_catalog` after each published price, variant, or availability change. The seed adds new inventory resources but **does not overwrite existing stock balances or reservations**. Adjust available quantities explicitly in the local database when the testing inventory policy changes. Checkout rejects a stale client price and stock below the required amount. This script refuses nonlocal databases.
5. Start the backend with `npm run ai:start` from the repository root (port `8013`) and the web app with `npm run dev --prefix apps/web`. Confirm `AI_BACKEND_URL` points at the backend's actual local port. The checkout is enabled only in local development; production builds do not expose test payment instructions.

## Identity and admin

- With no SMTP provider in `development` or `test`, verification and reset links are written to `apps/ai-backend/.private/customer-auth-outbox/`. Keep that directory private. Links place the one-use, 30-minute token in the URL fragment so it is not sent in the page request or access log. In any other environment an SMTP provider is required and delivery fails closed. Configure `CUSTOMER_SMTP_HOST`, `CUSTOMER_SMTP_PORT` (STARTTLS, normally 587), `CUSTOMER_SMTP_USER`, `CUSTOMER_SMTP_PASSWORD`, `CUSTOMER_SMTP_FROM`, and `CUSTOMER_AUTH_URL`. The sender domain must be permitted by the provider. Never print outbox contents or tokens in logs.
- To enable Google login, in [Google Auth Platform](https://support.google.com/cloud/answer/15544987?hl=en) configure the 52 Coffee branding and the intended audience; add authorized test users while the external app is in testing. In [Clients](https://developers.google.com/identity/protocols/oauth2/web-server), create an OAuth 2.0 **Web application** client and add the exact authorized redirect URI `http://localhost:3000/api/customer/google/callback` for the default local port (or `http://localhost:3001/api/customer/google/callback` for the isolated browser port). Scheme, host, port, path, and trailing slash must match the running web app exactly. Set `CUSTOMER_GOOGLE_REDIRECT_URI` on web and backend to that URI, `CUSTOMER_GOOGLE_CLIENT_ID` on both services, and `CUSTOMER_GOOGLE_CLIENT_SECRET` on backend only. Restart both services. Google login is unavailable until these are configured. An existing password account must first sign in and explicitly link the matching verified Google identity from My Account. Test new login, linking, cancellation, and redirect mismatch with the real provider before release.
- Create and verify a normal customer account first. To promote it on the local development database, set `CUSTOMER_ADMIN_EMAIL` and `PYTHONPATH=.` in the command environment and run `..\..\.venv\Scripts\python.exe -B scripts/promote_customer_admin.py` from `apps/ai-backend`. The real-order admin APIs require this role, the existing dashboard PIN session, and the backend admin key. The promotion script refuses other database names or remote hosts.

## Local test journey

Register, open the private outbox link, verify, login, add catalog items to cart, save an address in My Account, create a pending checkout order, view the actual configured QRIS or BCA instructions, upload a JPG/PNG/PDF proof, open the WhatsApp draft and press Send manually, then verify receipt in the admin Orders tab. Approval is a human assertion that funds were actually received. Rejected proof can be reuploaded. My Account and `/track` read owner-scoped database orders. The old browser demo orders remain separate in the dashboard.

The checkout price authority is a seeded snapshot of published coffee variants, cart accessories, and published espresso beans used by BYOB. The backend recalculates a blend from its component ratios and snapshot prices. New blends save their composition in the cart; legacy blend cart lines without composition must be rebuilt. All categories reserve finite synthetic testing stock inside the order transaction. Pending/rejected orders expire after `CUSTOMER_TEST_PAYMENT_HOURS` (1–168, default 24); the next order or order read cancels expired orders and restores stock. Manual cancellation of an unpaid order also restores stock. Approved payments consume the reserved stock. No live inventory feed or courier integration exists. The local flat test fee is displayed before order placement and stored with the order. Do not use these synthetic stock or shipping values for production transactions.

## Checks

From `apps/ai-backend`, run `$env:CUSTOMER_COMMERCE_IT='1'; .\.venv\Scripts\python.exe -B -m unittest app.test_customer_commerce`. Tests create and remove synthetic records on the local database, including accessory/closeout and blend cases. From the root run `npm run typecheck --prefix apps/web`, `npm run lint --prefix apps/web`, and `npm run build --prefix apps/web`. When `next dev` is already running, set `$env:NEXT_DIST_DIR='.next-commerce-build'` for the build so the two processes do not share `.next`.

## Manual browser check

Use one allowlisted test email on `http://localhost:3000`. Register, retrieve the verification link from the private dev outbox, verify, log in, and confirm My Account loads. Add coffee, an accessory, and a newly created BYOB blend to the cart. Save an address, open checkout, check the configured flat test fee and approximate total, then create an order for QRIS or BCA. Confirm the stored order total, original merchant image or private BCA instructions, and the payment deadline. Upload a **synthetic** JPG, PNG, or PDF proof and confirm `awaiting_verification`; opening WhatsApp should show a draft only. Use a verified local admin account plus the dashboard PIN to view the proof and **reject** the synthetic proof. Reupload, verify the rejection history and `/track`, then cancel or let an unpaid test order expire to check stock restoration. A synthetic approval may be used only on the isolated local database to verify state propagation; it creates a `paid` test fixture without received funds and must never be copied into financial records. In real operations, approve only after checking actual receipt of funds.

Automated local API integration covers register/login, reset/logout, ownership, server pricing, accessory and blend orders, stock exhaustion, expiry, proof upload, admin decisions, and tracking data. Browser interaction and Google provider login require separate verification; Google credentials and SMTP settings remain blank unless supplied by the owner.
